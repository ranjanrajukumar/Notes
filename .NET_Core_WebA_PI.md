## ASP.NET Core Web API + EF Core + Dapper

## 1. ASP.NET Core Web API Architecture

In an ASP.NET Core Web API project, the request generally flows:

```text
Client
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
EF Core / Dapper
  ↓
SQL Server
```

### Interview Answer
> “In my ASP.NET Core Web API project, the request generally flows from Controller to Service, then Repository or Data Access layer, and finally to the Database. The Controller handles the HTTP request and response, the Service contains business logic, the Repository handles data access, and EF Core or Dapper communicates with the database.”

**Shortcut:** Controller → Service → Repository → Database

---

## 2. Controller → Service → Repository

### Controller
Handles HTTP requests and responses.

### Service
Contains business logic.

### Repository
Handles database operations.

### Interview Answer
> “I keep responsibilities separated. The Controller handles HTTP requests, the Service handles business logic, and the Repository handles database operations. This improves maintainability, testability, and separation of concerns.”

---

## 3. Dependency Injection in Web API

### Interview Answer
> “Dependency Injection is a technique where dependencies are provided to a class from outside instead of creating them inside the class. ASP.NET Core provides a built-in dependency injection container. It helps reduce tight coupling and improves testability and maintainability.”

Example:

```csharp
builder.Services.AddScoped<IEmployeeService, EmployeeService>();
```

### Service Lifetimes

| Lifetime | Meaning |
|---|---|
| Transient | New instance whenever resolved |
| Scoped | One instance per HTTP request |
| Singleton | One instance for application lifetime |

## 4. Middleware Pipeline

### Interview Answer
> “Middleware is software that handles HTTP requests and responses as they pass through the ASP.NET Core pipeline. Middleware can perform tasks such as exception handling, authentication, authorization, logging, and CORS.”

```text
Request
 ↓
Exception Middleware
 ↓
Authentication
 ↓
Authorization
 ↓
Controller
 ↓
Response
```

### Use vs Run vs Map

- `Use()` → continues to next middleware.
- `Run()` → terminal middleware.
- `Map()` → creates a separate pipeline branch.

**Shortcut:** Use = Continue | Run = Stop | Map = Branch

## 5. Model Binding & Model Validation

### Model Binding

> “Model Binding takes data from the HTTP request, such as route, query string, body, or form data, and converts it into C# parameters or models.”

### Model Validation

Validation checks whether the received data is valid.

```csharp
public class Employee
{
    [Required]
    public string Name { get; set; }

    [Range(18, 60)]
    public int Age { get; set; }
}
```

### Interview Answer
> “Model Binding converts request data into C# parameters or models, while Model Validation checks whether the bound data satisfies the validation rules.”

## 6. IActionResult vs ActionResult<T>

### IActionResult

Represents an HTTP action result.

```csharp
public IActionResult GetEmployee(int id)
{
    if (id <= 0)
        return BadRequest();

    return Ok(employee);
}
```

### ActionResult<T>

Combines an HTTP action result with a strongly typed response model.

```csharp
public ActionResult<Employee> GetEmployee(int id)
{
    if (employee == null)
        return NotFound();

    return Ok(employee);
}
```

### Interview Answer
> “IActionResult represents an HTTP action result. ActionResult<T> combines an HTTP action result with a strongly typed response model. I prefer ActionResult<T> when the API has a specific response type.”

## 8. Entity Framework Core

### Interview Answer
> “Entity Framework Core is an ORM for .NET that allows us to work with databases using C# objects instead of writing SQL for every operation. It provides features such as LINQ queries, change tracking, relationships, migrations, and database interaction through DbContext.”

Example:

```csharp
var employees = await _context.Employees
    .Where(x => x.Status == "Active")
    .ToListAsync();
```

---

## 9. EF Core Tracking vs No-Tracking

### Tracking

EF Core tracks changes to entities.

```csharp
var employee = await _context.Employees
    .FirstOrDefaultAsync(x => x.Id == id);

employee.Name = "Raju";

await _context.SaveChangesAsync();
```

### No-Tracking

For read-only queries:

```csharp
var employees = await _context.Employees
    .AsNoTracking()
    .ToListAsync();
```

### Interview Answer
> “Tracking allows EF Core to track entity changes so they can be saved using SaveChanges. For read-only operations, I use AsNoTracking because it avoids unnecessary change tracking and can improve performance.”

**Shortcut:** Update → Tracking | Read only → AsNoTracking

---

## 10. Include() / Eager Loading

`Include()` loads related data along with the main entity.

```csharp
var employees = await _context.Employees
    .Include(x => x.Department)
    .ToListAsync();
```

### Interview Answer
> “Include is used for eager loading in EF Core. It allows us to load related entities as part of the query.”

## 11. EF Core Migrations

### Interview Answer
> “EF Core Migrations are used to manage changes in the database schema based on changes in our entity models.”

Typical commands:

Add-Migration InitialCreate

```

```

## 12. Dapper

### Interview Answer
> “Dapper is a lightweight micro-ORM for .NET. It allows us to execute SQL queries and map the results directly to C# objects. It gives more control over SQL compared to a full ORM like EF Core.”

Example:

```csharp
var employees = await connection.QueryAsync<Employee>(
    "SELECT * FROM Employee WHERE DepartmentId = @DepartmentId",
    new { DepartmentId = 10 });
```

---

## 13. EF Core vs Dapper

| EF Core | Dapper |
|---|---|
| Full ORM | Micro-ORM |
| LINQ support | SQL-focused |
| Change tracking | No built-in change tracking like EF Core |
| Migrations | Supports migrations |
| More abstraction | More control over SQL |
| Good for complex domain/data models | Good for lightweight/high-control queries |

### Interview Answer
> “EF Core is a full ORM that provides LINQ, change tracking, relationships, and migrations. Dapper is a lightweight micro-ORM that focuses on executing SQL and mapping results to objects. I would choose EF Core when I need ORM features and Dapper when I need more direct control over SQL and lightweight data access.”

## 14. Repository Pattern

### Interview Answer
> “Repository Pattern separates data-access logic from business logic. The Repository is responsible for database operations, while the Service handles business rules.”

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

### Why?

- Separation of concerns
- Maintainability
- Testability
- Centralized data access

## 15. Unit of Work

### Interview Answer
> “Unit of Work groups multiple related database operations into a single transaction. If all operations succeed, we commit them. If an operation fails, we roll back the transaction.”

Example:

```text
Save Employee
     +
Save Employee Address
     +
Update Department
     ↓
One Transaction
     ↓
COMMIT
```

If something fails:

```text
ROLLBACK
```

**Important:** Sending an email is an external system and generally should not be treated as part of the same database transaction.

---

## 16. Transactions in Web API

Example:

1. Create an Order
2. Create Order Items
3. Update Product Stock

These operations should succeed or fail together.

```text
BEGIN TRANSACTION

Create Order
Create Order Items
Update Stock

COMMIT
```

If something fails:

```text
ROLLBACK
```

### Interview Answer
> “For operations that must succeed or fail together, I use a database transaction. For example, creating an order, saving order items, and updating stock can be handled within one transaction. If all operations succeed, I commit; otherwise, I roll back.”

## 17. API Performance Optimization

### Interview Question
**Your API is slow in production. What will you check?**

### Strong Answer
> “First, I identify where the bottleneck is using logs and monitoring. I check whether the issue is in the application, database, or external service. For database issues, I check slow queries, execution plans, indexes, unnecessary joins, and excessive database calls. I also check pagination for large datasets, caching for frequently accessed data, and asynchronous I/O for external or database operations. After optimization, I test the API and monitor it again.”

**Shortcut:** Logs → DB → Query → Index → Pagination → Cache → Async → Monitor

## 18. Scenario — EF Core API Is Slow

Example:

```csharp
var employees = await _context.Employees
    .Include(x => x.Department)
    .Include(x => x.Attendance)
    .ToListAsync();
```

If there are millions of records, this can load too much data.

### Improvements

- Pagination
- `AsNoTracking()` for read-only data
- Projection with `Select()`
- Proper indexes
- Avoid unnecessary `Include()`
- Select only required columns

Example:

```csharp
var employees = await _context.Employees
    .AsNoTracking()
    .Where(x => x.Status == "Active")
    .Select(x => new EmployeeDto
    {
        Id = x.Id,
        Name = x.Name
    })
    .Skip((pageNumber - 1) * pageSize)
    .Take(pageSize)
    .ToListAsync();
```

## 19. Scenario — EF Core or Dapper?

### Interview Answer
> “I would choose Dapper when I need direct control over SQL, lightweight data access, or highly optimized queries. I would choose EF Core when I need ORM features such as LINQ, change tracking, relationships, and migrations.”
